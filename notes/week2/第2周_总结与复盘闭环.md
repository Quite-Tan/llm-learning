## 二、知识地图：chat.py 200 行拆成五块

```
chat.py
├─ 类与对象   → 状态封装（self.dict）+ 职责拆分（四个类）
├─ 文件 IO    → Path + json + 编码兜底 → 程序有记忆
```

一句概括：**这五块 = 任何 CLI 工具 / Agent 框架的骨架。** LangChain 的 AgentExecutor、OpenAI CLI、git 本身，结构都是这一套。所以这周不是在学 Python 语法，是在拆一个通用架构。

## 四、踩坑记录（本周六个实证）

### 1. 类属性共享坑（可变对象）

```python
class C:
    shared = []          # 类属性，全体共用一份
    def __init__(self):
        self.logs = []   # 实例属性，各有一份
```

`id(a.shared) == id(b.shared)` → `True`；`id(a.logs) == id(b.logs)` → `False`。

**规则**：可变的、会被修改的状态，一律放 `__init__` 里初始化。不可变的默认值模板（如 `DEFAULTS = {...}`）可以写成类属性。

### 2. ensure_ascii=False

默认 `True` 会把中文转成 `\u9ed8\u8ba4`。功能等价但人类不可读，手动改配置和 git diff 时完全没法用。

同一行里三个参数各管各的，不能混：

- `encoding="utf-8"` → 文件编码（Windows 默认 cp936）
- `ensure_ascii=False` → 中文原样输出
- `indent=2` → 缩进格式化

### 3. 异常捕获顺序

`UnicodeDecodeError` 是 `Exception` 的子类，是包含关系不是并列。宽的在上会截胡所有子类，Python 3.12+ 对这种死代码直接报 `SyntaxWarning`。

更危险的是 `except Exception` 会吞掉自己的拼写错误（`jason.loads`），让你花半小时查文件和编码。

### 4. 裸 except: 关不掉程序

`KeyboardInterrupt` 继承自 `BaseException`，不在 `Exception` 下面。所以 `except Exception` 抓不到它、Ctrl+C 依然有效；但裸 `except:` 能抓到它，于是用户按 Ctrl+C 退不出去。这就是"永远不用裸 except"的技术根源。

### 5. flush=True 缺一流式就废

`end=""` 不换行 → 行缓冲永不触发刷新 → token 全憋在内存里 → 循环结束一换行整句蹦出。

- `end=""` 负责"不换行连着写"
- `flush=True` 负责"别攒着马上显示"

### 6. split(maxsplit=1)

`/doc load D:\TanTian\LLM\笔记.md` 不加 `maxsplit=1`，路径会被切成 `['load', 'D:\\TanTian\\LLM\\笔记', 'md']`。

只要涉及带空格的路径或句子，就必须限制切分次数。

## 五、认知升级（三条）

### 1. 函数封装动作，类封装「动作 + 它自己的数据」

全局变量方案的三个死穴：状态散落、无法多开、无法复用。类的价值在于"可以复制多份的独立状态"。

### 2. print 是给人看的，full_reply 是给模型看的

流式模式下必须手动重建完整文本存进 history，API 不会替你做。这也是第 1 周"失败的消息不能进历史"那个坑的流式版本。

### 3. stream=True 拿到的是水龙头，不是答案

`client.chat(...)` 几乎瞬间返回，它没等模型生成完。你不迭代，token 就不会流出来。总耗时和非流式差不多，只是把等待摊平了。

## 八、收尾动作：闭卷重写 chat_lite.py

**规格**（简化版，够用就行）：

1. 一个类，`__init__` 初始化 history（带 system prompt）和 model 名。
2. `send(msg)`：append 用户消息 → 调 ollama（非流式即可）→ append 助手回复 → 打印。
3. `/clear` 清空历史、`/model <名字>` 切换模型、`/save` 存 JSON、启动自动加载。
4. 主循环：`input` + `strip` + `split(maxsplit=1)` + `KeyboardInterrupt` 捕获。
5. 连不上 Ollama 时打印提示，且那条消息不进历史。
6. 不要求流式、不要求参数调节、不要求文档注入。

**判断标准**：能跑通、报错不崩、重启能恢复对话。

**卡住了怎么办**：卡在哪一行就停在哪一行，把卡点发过来。卡点本身比顺利写完更有信息量——它精确标出了哪块只是"看懂了"而不是"会写了"。

## 九、为什么第 3 周继续吃透 Ollama，不换云端 API

原计划第 3 周是「Ollama API 深入 + prompt 工程」，曾提议提前上云端 API，现撤回，理由三条：

1. **变量控制。** 本地模型和云端模型的效果差异里，混着"模型能力"和"prompt 写法"两个变量。先把 prompt 工程练到能量化评价，再换引擎，才分得清是引擎好还是你写得好了。
2. **第 3 周的考核不是效果，是架构弹性。** 考核问题是：换一套 prompt 要不要改代码？换一个小模型要不要改评测脚本？这两个问题在本地就能测，上云不增加任何信息量。
3. **RAG 之后谈云才有意义。** 向量检索 + 召回质量评测做完，再考虑云端 embedding 和长上下文，那时每一分钱都花在刀刃上。

所以第 3 周主线不变：`prompts/` 模板库 + `eval_chat.py` 评测脚本 + 一份量化对比报告。云端 API 整体后移到第 4 周之后作加分项。
