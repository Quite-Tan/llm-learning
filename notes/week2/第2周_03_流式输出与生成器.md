## 一、同一个 API，两种返回类型

`client.chat(...)` 这一个调用，`stream` 参数决定了返回值的本质：

| stream= | 返回什么                   | 含义                   |
| ------- | ---------------------- | -------------------- |
| `False` | `ChatResponse`（完整响应对象） | 回答已生成完毕，一次性给你        |
| `True`  | **生成器/迭代器**            | 回答还没生成，是一个“以后逐段吐”的凭证 |

```python
r1 = client.chat(model="qwen3:4b", messages=msgs, stream=False)
print(r1["message"]["content"])      # 直接取全文

r2 = client.chat(model="qwen3:4b", messages=msgs, stream=True)
print(r2)                            # <generator object ...>，不是答案！
```

> **关键认知**：`stream=True` 拿到的不是答案，而是一个水龙头。程序在 `client.chat(...)` 这行几乎是瞬间返回的——它没等模型生成完，只是把水龙头递给你。你不迭代，token 就不会流出来。

**体验差别**：非流式要等 3~8 秒整段蹦出；流式是边生成边吐，第一字 0.5 秒内出现。总耗时差不多，但等待被摊平了，主观上快很多。

## 二、for chunk in stream 背后：迭代器协议

`for` 循环要求对象遵守迭代器协议，两个魔术方法：

```python
def __iter__(self): ...   # for 一开始调，拿到迭代器
def __next__(self): ...   # 每转一圈调一次；没了就抛 StopIteration
```

`for chunk in stream` 实际执行的是：

```python
it = iter(stream)
while True:
    try:
        chunk = next(it)
    except StopIteration:
        break
```

`list`、`str`、`dict`、文件对象、生成器全都实现了这套协议。所以能对一个还没生成完的输出用 `for`——语法上和遍历列表完全统一，只是数据是现用现生成的。

## 三、yield：自己造一个水龙头

```python
import time

def fake_stream(text):
    for ch in text:
        yield ch
        time.sleep(0.08)
```

### yield vs return（本层核心）

|           | return        | yield             |
| --------- | ------------- | ----------------- |
| **调用后**   | 执行到底，返回值，函数销毁 | 不执行，立刻返回生成器对象     |
| **再次取值时** | ——            | 从上次 `yield` 处继续执行 |
| **状态**    | 每次从头跑         | 局部变量、执行位置原地保留     |

带 `yield` 的叫**生成器函数**。它被调用时一个字节码都不跑，只返回生成器；只有你 `next()` 它时，它才活一段，跑到下一个 `yield` 交出值、再原地冻结。这就是**惰性求值**：不取不生成。

> **为什么对大模型至关重要**：模型逐 token 生成，天然“一段一段产出”。生成器让边生成边消费成为可能。

## 四、flush=True 为什么必须写

去掉它，流式效果当场消失。原因在 `print` 的**行缓冲机制**：

1. `print` 的内容先进内存缓冲区，攒够了或遇到换行才真正刷到屏幕。
2. `end=""` 不换行 → 缓冲区永不触发刷新 → token 全憋在里面。
3. 结果：循环跑完、最后那个 `print()` 一换行，整句一次性蹦出——跟非流式没区别。

**`flush=True` = 这次 print 立刻清空缓冲区、强行刷到屏幕。**

- `end=""` 负责“不换行、连着写”
- `flush=True` 负责“别攒着、马上显示”

**两个缺一，流式就废。**

## 五、为什么要自己拼 full_reply

这是最容易被忽略却最致命的一点。

流式输出时，模型的话是一段一段吐的。如果不把片段拼起来，`self.history` 里那条 assistant 消息就是空的。下一轮 `_build_messages()` 组装上下文时，模型看不到自己上一轮说了什么，直接失忆。

```python
full_reply = ""
for chunk in stream:
    piece = chunk["message"]["content"]
    full_reply += piece          # 边显示边把碎片拼回完整一句
    print(piece, end="", flush=True)

self.history.append({"role": "assistant", "content": full_reply})
```

> **`print` 是给人看的（逐字爽），`full_reply` 是给模型看的（必须完整）。API 不会替你留副本。**

**隐患加固**：如果 `for` 中途断流，`full_reply` 只有半句。`except` 分支要把这条半截的 assistant 也 `pop` 掉，或者把 `append` 放在 `try` 正常走完的分支里。

## 六、三个破坏性实验（比顺跑一遍收获大）

| 改动                 | 现象                                                                  | 说明的道理                     |
| ------------------ | ------------------------------------------------------------------- | ------------------------- |
| `yield` 改 `return` | 不再返回生成器，而是返回第一个字符；`for` 去遍历这个字符串，行为全乱                               | 生成器函数被调时不执行、只返回生成器        |
| 去掉 `flush=True`    | 打字机效果消失，整句最后一次性蹦出                                                   | 行缓冲憋住了输出                  |
| 删掉 `return full`   | `len(result)` 报 `TypeError: object of type 'NoneType' has no len()` | 函数不写 `return` 默认返回 `None` |
