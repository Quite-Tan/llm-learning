## 二、踩坑记录

### 坑 1：Python 报 `ConnectionError: Failed to connect to Ollama`

终端 `ollama run` 正常，但 Python 脚本连不上。

排查顺序（以后照这个查）：

1. `ollama list` —— CLI 可用、模型已下载
2. `ollama ps` —— 后台服务活着
3. `netstat -ano | findstr 11434` —— 端口在监听；无输出则执行 `ollama serve`
4. `where python` —— 确认激活的是 `envs\llm` 里的 Python
5. **代理环境变量**（最隐蔽）

根因：系统挂了代理，`ollama` 库把 localhost 请求也转走了。

解决（必须在 `import ollama` 之前）：

````python
os.environ["OLLAMA_HOST"] = "http://127.0.0.1:11434"
os.environ["NO_PROXY"] = "localhost,127.0.0.1"
坑 2：环境变量设置顺序
os.environ 写在 import ollama 后面是无效的——库在导入时就读完了配置。这类问题没有报错提示，只会表现为“改了没生效”，排查成本很高。
规则：所有配置型环境变量，一律放在文件最顶部、所有第三方 import 之前。
坑 3：失败的消息不能进历史
流式输出中途断连时，如果用户消息已经 append 进 history，下一轮会带着残缺上下文继续跑，模型开始胡言乱语。
解决：except 分支里 self.history.pop()，把那条没得到回复的消息撤掉。
坑 4：Windows 中文文件编码
Path.read_text(encoding="utf-8") 读自己写的中文笔记可能直接抛 UnicodeDecodeError。
解决：utf-8 失败回退 gbk。
python

编辑

try:
    raw = p.read_text(encoding="utf-8")
except UnicodeDecodeError:
    raw = p.read_text(encoding="gbk")
坑 5：文档全文硬塞会撑爆小模型
一开始没设上限，把整篇 md 塞进 system prompt，3B 模型直接忘了人设、回答变短、还开始编造。
解决：MAX_DOC_CHARS = 8000 硬截断，并明确告诉模型“文档里没有就直说”。
后续：这就是第 4 周 RAG 要解决的问题——从“全文硬塞”升级为“只塞相关片段”。这段代码留着做对比基线。
三、两个版本的差异（chat.py v1 → v2）
表格
能力	v1	v2
多轮上下文	✅ history 列表	同左
流式输出	✅	✅ + 可开关（/set stream off）
切换模型	✅	同左
参数调节	❌ 写死	✅ temperature / top_p / num_predict / stream，落盘 params.json
会话持久化	❌ 退出即丢	✅ 自动存 sessions/*.json，启动自动恢复 default
外部文档	❌	✅ /doc load，最原始的 RAG
异常健壮性	一般	Ctrl+C 也保存、连接失败回滚历史
架构上的一个改进：v1 是把历史直接传给 API；v2 改成了「每次重新组装消息」——system → 文档 → 历史 → 新提问。这样文档的载入和清除不用去修改历史列表，状态管理清晰很多。这个模式后面做 RAG 时会继续沿用。
````
